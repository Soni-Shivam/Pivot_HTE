# Faultline live visualization (ROS 2 Jazzy, RViz, Lichtblick HMI)

Display only: everything here reads the world and never feeds back into the run.

## Start / stop

```bash
viz/launch_viz.sh start      # foxglove_bridge, hmi_latch, RViz, HMI web server, Firefox on DISPLAY=:2
source viz/env.sh && .venv/bin/python viz/demo_live.py --family cut_in    # or lead_brake (default)
viz/launch_viz.sh stop       # status: viz/launch_viz.sh status; logs and pids in runs/viz/
```

`demo_live.py` runs a CARLA episode with the chase camera and the bridge. The adversary is a local script
(`scripted-baseline`, never 0G): lead_brake = MAINTAIN then BRAKE_HARD from `--brake-cp`; cut_in = KEEP_LANE,
CUT_IN_AGGRESSIVE at `--brake-cp`, then BRAKE_HARD. It waits on the CARLA flock like any other run and always
closes the world. `viz/env.sh` sources Jazzy and pins `ROS_DOMAIN_ID=42`, localhost only (another stack on this
machine uses domain 55).

Window layout on the 1920x1200 desktop: chase camera top-left (1280x784, from the run), RViz bottom-left strip
(1280x416), HMI right column (640x842), live agent terminal bottom-right (640x330). There is no xdotool/wmctrl, so
`viz/xplace.py` moves windows by title (xwininfo + libX11 via ctypes).

## HMI: Lichtblick, not Foxglove Studio desktop

Foxglove Studio 3.5.0 desktop shows a sign-in dialog (device code at foxglove.dev/activate) for a fresh data dir,
and the signed-in default data dir belongs to an instance already running on display :1, so it cannot be opened
non-interactively. The HMI instead uses Lichtblick (the MPL-2.0 Foxglove Studio fork, already installed by SeDriCa's
`install_lichtblick.sh` in `~/.local/share/sedrica_hmi/lichtblick-web`), served by `viz/hmi_web.py` on
http://localhost:8780/ and opened in Firefox; the URL carries `ds=foxglove-websocket`, `ds.url=ws://localhost:8765`
and `layoutUrl=…/faultline_hmi.json`, so it connects and loads the layout with no click. To use Foxglove desktop
anyway after signing in once: `python3 viz/foxglove_layout.py --install <data dir>` then open
`foxglove://open?ds=foxglove-websocket&ds.url=ws%3A%2F%2Flocalhost%3A8765&layoutId=faultline-hmi`.

`viz/faultline_hmi.json` is generated by `viz/foxglove_layout.py` (recipe from SeDriCa `make_*layout.py`): mode,
safe_halt and decision text, a 3D panel following `ego` (LiDAR turbo by z, lanelet map, GT and track boxes), plots
of ego vs adversary speed, LiDAR vs GT gap, TTC, ego accel/steer, and the adversary action.

Workarounds, each found on this machine:
- Lichtblick 1.29's Indicator and StateTransitions panels never received data from the bridge (topics advertised
  before or after load, after a reload, String/Float64/Bool alike) while RawMessages and Plot did; mode, safe_halt
  and adversary action are RawMessages text panels.
- foxglove_bridge runs with `capabilities:=[connectionGraph,assets]`: read-only, no client publishing.
- `viz/hmi_latch.py` republishes the lanelet map and the ego→lidar static TF every 2 s (Lichtblick missed the
  one-shot latched copy) and holds the HMI topics advertised.
- Firefox runs from a fresh profile each start (`~/snap/firefox/common/faultline-hmi`), page zoom 0.8, a Chrome UA
  string (hides Lichtblick's unsupported-browser banner), and the injected page script presses `[` once to close
  the left sidebar. Snap Firefox ignores our signals, so stop closes it with XKillClient.

## Topics (all stamped with sim time `tickstate.t_s`)

| topic | type | notes |
|---|---|---|
| `/tf` | tf2_msgs/TFMessage | `map`→`ego` (actor transform) |
| `/tf_static` | tf2_msgs/TFMessage | `ego`→`lidar` (x 1.5, z 1.9) |
| `/clock` | rosgraph_msgs/Clock | RViz runs with `use_sim_time` |
| `/faultline/lidar` | sensor_msgs/PointCloud2 | frame `lidar`; x, y, z, intensity float32, point_step 16 |
| `/faultline/tracks` | visualization_msgs/MarkerArray | LiDAR tracks (`world.tracks`), cyan, label id + speed |
| `/faultline/gt` | visualization_msgs/MarkerArray | actor boxes: ego green, adversary orange |
| `/faultline/lanelet_map` | visualization_msgs/MarkerArray | borders + centrelines of `maps/Town10HD_Opt.osm`, transient local |
| `/faultline/ego/odom` | nav_msgs/Odometry | |
| `/faultline/ego/{speed,accel,steer}`, `/faultline/adversary/speed`, `/faultline/gap_lidar`, `/faultline/gap_gt`, `/faultline/ttc` | std_msgs/Float64 | NaN when undefined (no LiDAR gap / not closing) |
| `/faultline/adversary_action`, `/faultline/decision`, `/faultline/mode` | std_msgs/String | decision e.g. `cp 3 · BRAKE_HARD · 0g · req ffa5d0… · 2215 ms` |
| `/faultline/safe_halt` | std_msgs/Bool | |

`mode` is RUNUP before the first decision, EXECUTING after a valid one, SAFE_HALT after a `source: "none"` entry, and
AWAITING_0G when no tick has arrived for 0.25 s after the run-up (the loop is blocked on the decider).

## Frames: the y flip

CARLA is left-handed (x forward, y right, z up); ROS is right-handed. Everything uses
`x_map = x_carla, y_map = -y_carla, z_map = z_carla, yaw_map = -yaw_carla` (`faultline/rosbridge.py: to_map,
yaw_quat`); the LiDAR cloud flips the sensor y the same way (`lidar_points`). The Lanelet2 map
(`faultline/lanelet_export.py`, 168 lanelets, one per lane segment incl. junction connectors, projector
`LocalCartesian(0, 0)`) is written in the same frame; its centrelines sit 0.03 m mean / 0.28 m max from CARLA
waypoints.

## Bridge cost

Measured in `demo_live.py` (published per tick inside the 20 Hz loop): mean 1.3–2.5 ms, p95 2–5 ms; single outliers
up to ~300 ms were seen twice (one tick each).

## Wiring `--ros` into `python -m faultline run`

Bridge must attach after `world.reset()` (actors exist, and `ChaseView.attach` inside reset overwrites
`world.on_tick`; the bridge then fans out). In `cmd_run`, around each `run_episode(make_world(...), ...)`:

```python
r.add_argument("--ros", action="store_true", help="publish to ROS 2 (source viz/env.sh first; CARLA only)")
# in cmd_run, replacing make_world(...) inside run_episode(...):
world = make_world(a.world, out, a.view, a.display, family=a.family)
bridge = None
if a.ros:
    from faultline.rosbridge import RosBridge
    bridge, reset = RosBridge(), world.reset
    world.reset = lambda s: (reset(s), bridge.attach(world))
try:
    m = run_episode(world, decider, s, out, ...)
finally:
    if bridge:
        bridge.close()
```

Cleaner long-term hook (needs an edit to `carla_world.py`, not done here): a list `self.observers = []` in
`CarlaWorld.__init__`, `for o in self.observers: o.attach(self)` after `self.view.attach(self)` in `reset`, and
`o.close()` in `close()`; then `--ros` is `world.observers.append(RosBridge())`.

## Tests

`tests/python/test_rosbridge.py` (frame conversion, PointCloud2 layout and y flip, mode/TTC/decision line; a
`carla`-marked test receives a >1000-point cloud on `/faultline/lidar`) and `tests/python/test_lanelet_export.py`
(border sides, round trip on a tiny map). ROS tests skip without `rclpy`. With ROS sourced, run pytest with
`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` (ROS's pytest plugins need PyYAML, which the venv lacks; `rosbridge` appends
Ubuntu's `dist-packages` after the venv for rclpy's own `yaml` import).
